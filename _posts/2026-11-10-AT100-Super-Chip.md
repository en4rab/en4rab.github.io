## What the AT100 is

The AT100 is a **programmable multi-protocol transponder emulator** — a blank, sold for Autel key-programming tools, that can be told to present itself as a HITAG2, an EM4102, a Megamos, a Texas DST and so on. It is the Autel counterpart to the Xhorse super chips from the [XT27A]({% post_url 2026-10-29-XT27A-Super-Chip %}) and [XT136]({% post_url 2026-10-31-XT136-Super-Chip %}) posts, but where the Xhorse chips invent their own `XHORSE`/`XMICRO` channel and a bespoke LFSR cipher, the AT100's *management* interface is plain **stock HITAG2** — HITAG2 BPLM from reader to tag, HITAG2 Manchester back, and the ordinary Philips/NXP 48-bit stream cipher that the Proxmark3 already implements in `common/hitag2/hitag2_crypto.c`. No custom channel, no custom cipher.

What makes it an *emulator* is that three things have to be kept apart:

| Layer | Where it lives | Changes when you re-type the chip? |
|---|---|---|
| **Device UID** — 32-bit, `0x83xxxxxx`, returned in clear before auth | not in the page space | **No** |
| **Device key** `9F63A5E8B14B` — authenticates the management session; shared by every blank | not in the page space (low half mirrored at page `0xFC`) | **No** |
| **Emulation page space** — 256 pages × 32 bits, addressed `0x00`–`0xFF` by post-auth commands; `0xFE` is the type register | the low pages hold the emulated image; `0xFE` holds the type | **Yes** |
{: .wrap-cells }

Configuring the chip is then one idea: **authenticate, write the type code to page `0xFE`, then write that type's image into the low pages.** The device UID and key are provably independent of the image — one blank was re-typed 15 times across 24 captures and still authenticated with the same key and reported the same UID every time.

## The physical layer

Same sampling as the Xhorse traces: one `.pm3` sample is one T<sub>0</sub> = 8 µs (125 kHz, after envelope detection).

- **Reader → tag: HITAG2 BPLM.** The field drops briefly before every bit; an `18–22` T<sub>0</sub> gap is a `0`, `26–32` T<sub>0</sub> is a `1`.
- **Tag → reader: HITAG2 Manchester** (~`32` T<sub>0</sub> per symbol), opening with the HITAG2 `11111` start-of-frame.
- **The AT100 load-modulates hard** — its reply dips far enough to look like a reader field pulse — so the decoder uses a lower reader threshold throughout. (An earlier version of this post claimed only the read traces needed that; they all do.)

The Autel drops the field between almost every frame (13–150 ms), so each session in a trace is a fresh power-up and a fresh crypto session.

## A session, start to finish

### The wake handshake (all flows)

The AT100 is **not** reachable by the standard HITAG2 entry sequence. Sending it a HITAG2 `START_AUTH` gets no answer. Entry is instead a tiny handshake of the chip's own:

```text
R>T  1010                   4-bit wake
T>R  1010                   the tag echoes it verbatim
R>T  1111100000             get-UID
T>R  <32-bit UID>           e.g. 0x836BC7C7 -- cleartext
```
{: .nolineno }

That `1111100000` looks like it might be a HITAG2 "read page 0", but it is not — it is the AT100's own command framing, a 5-bit word `11111` followed by its complement `00000`, the same `{word}{~word}` shape used by every post-auth command. The UID it returns is the chip's **device** serial and never changes, whatever you program.

> **Correction.** The identify traces open with a long probe sweep — a 40-bit `0x1001002E3E` opener, a `0011`, some 5-bit HITAG2 commands, an `0xFF` — interleaved with `1110` and `FFFF…` frames. The first version of this post read those as the AT100's anticollision replies. They are not tag replies at all: they rail to ±127 and are the *reader's* own, much slower second modulation, the Autel probing for some non-HITAG2 transponder. **The AT100 answers none of the probe sweep.** It only wakes to the `1010` handshake.
{: .prompt-warning }

### Authentication (fixed IV)

```text
R>T  {nR}{aR}  = 64 bits    nR = 0xED355308 (cleartext IV), aR = keystream(32) ^ 0xFFFFFFFF
T>R  <32-bit>               encrypted -- the current page-0xFE type word
```
{: .nolineno }

The reader IV **`nR = 0xED355308` is identical in every one of the 85+ captured sessions, on every blank.** Because the nonce is fixed, `aR` depends only on key and UID, and one capture per tag is enough to recover the key — which is exactly how a HITAG2 deployment is *not* supposed to behave (the reader nonce should be random).

The 48-bit key recovers from a single `(UID, nR, aR)` triple with the Proxmark3's own bundled attack (`tools/hitag2crack/crack5`, the "HiTag2 Hell" state recovery), and the repo's reference cipher then checks it against the rest. It is the **same key on every blank**:

```text
key = 9F63A5E8B14B
```
{: .nolineno }

| UID | aR | verifies |
|---|---|---|
| `8358BE8C` | `76D8A24C` | ✓ |
| `836BC7C7` | `53AFB236` | ✓ |
| `83240599` | `D421F8D0` | ✓ |
| `831CBB49` | `3E1E1B81` | ✓ |
| `836B61C0` | `C5CF2336` | ✓ |
{: .wrap-cells }

The decoder in Fig. 1 runs this same cipher in your browser, so you can watch each `aR` verify and each page decrypt as you click through the table. The key's low half, `A5E8B14B`, is also readable at page `0xFC`; the identify flow reads exactly that one page — it is the Autel's "is this a genuine AT100" check.

> **Correction.** The first version called the 32-bit frame the tag sends right after auth "the constant `0x9B290A9B`". It is not constant: it is the **live contents of page `0xFE`, the type register**. It only looked constant because all six early captures were of factory-fresh blanks, and `9B290A9B` is the factory default (type ID4D). The upside is that a bare auth, with no commands at all, already tells you the chip's current emulated type — which is exactly what the Autel's *detect* flow uses it for.
{: .prompt-warning }

## The command format

After auth, every frame — commands, tag echoes and page data alike — is encrypted with one continuing keystream, consumed in strict on-air order. A command is a 20-bit frame carrying a **10-bit word sent twice, true then complemented** (`{W}{~W}`). The word is `op:2 | page:8`:

| `op` | Meaning |
|---|---|
| `01` | **READ** page — tag replies with the 32-bit page |
| `10` | **WRITE** page — tag echoes the 20-bit command, then the reader sends the 32-bit data |
{: .wrap-cells }

```text
READ :  R>T {0x1FE}{0x201}            T>R <page 0xFE>
WRITE:  R>T {0x2FE}{0x101}            T>R {0x2FE}{0x101} (echo)   R>T <32-bit data>
```
{: .nolineno }

The address is a full 8 bits, so the page space is **256 pages × 32 bits = 1 KiB**. A write is not acknowledged after the data; the Autel just waits ~98 ms for the EEPROM and sends the next command. (That self-checking `{W}{~W}` structure, incidentally, is what makes the whole decode trustworthy — a wrong keystream could not produce hundreds of valid complement pairs, nor make every tag write-echo match its command bit for bit.)

## Memory map

One 8-bit page address space, split into an emulation region and a device region:

| Pages | Role |
|---|---|
| `0x00`–`0x27` | the emulated transponder image; the meaning of each page is type-dependent (below). The biggest image, ID8A's, reaches page `0x27` |
| `0x3A`–`0x3D` | extra registers for the Texas ID4D / ID4E family (`0x3C` selects DST40 vs DST80) |
| `0x50`, `0xC8`, `0xF0`–`0xF4` | extra pages used by MQB49 / ID5C (its serial goes to `0xC8`, not `0x00`) |
| `0xFC` | **device-key page** — constant `A5E8B14B`, the low half of the device key. Read-only |
| `0xFE` | **type / configuration register** — persistent, auto-returned after auth |
{: .wrap-cells }

Page `0xFE` really is persistent and really is the type: across a 15-capture chain on one chip, the type word each `set` reads back at the start always equals whatever the previous `set` wrote. A factory blank holds `0xFE = 9B290A9B`, so **an AT100 ships configured as type ID4D.**

### The type codes

Page `0xFE` encodes the emulated type as `b3 b2 b1 b0` with `b0 = 0x9B` and `b1` the type index. The decoder names them from this table:

| Autel type | `0xFE` word | | Autel type | `0xFE` word |
|---|---|---|---|---|
| ID11 / ID12 / ID13 | `9B04019B` | | 7939 / ID49 | `8F1C079B` |
| 7936 / ID46 | `8F08029B` | | ID5C / MQB49 | `8F20089B` |
| 7946 | `8F0C039B` | | ID4C | `9B25099B` |
| 7937 | `8F10049B` | | ID4D / ID4D-80 | `9B290A9B` |
| 7938 / ID47 | `8F14059B` | | ID4E | `9B2D0B9B` |
| ID4A | `8F18069B` | | ID8A | `9B310C9B` |
| ID48 | `8F360D9B` | | MQB / ID8B | `8F3A0E9B` |
| ID8C | `8F3E0F9B` | | | |
{: .wrap-cells }

ID11/12/13 share one code (the variant is carried in page `0x00`), and so do ID4D and its 80-bit variant (distinguished by page `0x3C`). The config word also has two redundant fields that partition the index range into four blocks — suggestive of four internal emulation engines, but fully determined by the index in everything captured, so just a hypothesis.

## What a "set" actually writes

The `set` traces are the interesting ones — each is the Autel programming the blank into one emulated identity. A few, selectable in Fig. 1, give the flavour of how different the images are:

- **7936 / ID46** — the factory MIKRON HITAG2 image. Page `0x00` is a fresh serial, `0x01`/`0x02` spell the HITAG2 key `"MIKR"` + `"..ON"`, `0x03` is the config/password `06AA4854`. These are the same bytes the XT136 writes on a reset.
- **ID13 — EM4102.** Pages `0x01`/`0x02` are a **literal, fully valid 64-bit EM4102 frame**: nine header ones, ten rows of four data bits with correct row parity, four correct column-parity bits and a stop bit, carrying ID `04 56 B3 07 C8`. (Its siblings ID11/ID12 use the same two pages for other fixed-code formats, selected by a mode field in page `0x00`.)
- **ID48 — Megamos Crypto.** An eight-page Megamos block with `AAAAAAAA` lock words at `0x06`/`0x07`. MQB / ID8B is built on top of the same block with four extra pages.
- **ID5C / MQB49.** The odd one out — its serial goes to page `0xC8`, and it scatters constants across pages `0x0C`, `0x0D`, `0x11`, `0x50` and `0xF0`–`0xF4`.
- **ID8A — Texas DST128.** A big 40-page image (`0x00`–`0x27`); only the even pages carry payload.
- **ID4C** writes an 8-byte UID plus a **CRC-16/XMODEM** in the high half of page `0x02` (verified against the captured value).

The programming order is almost always the same: `WRITE 0xFE = <type code>`, then the image pages. The handful of exceptions are real and reproducible — the fixed-code family writes page `0x00` first, 7937/7946 program the chip as ID46 and then re-type it, and MQB49 writes its serial up front — and are listed in full in `docs/at100.md`. Serial-like values are generated fresh by the Autel on every run, so those bytes differ from capture to capture; everything else is constant.

## Preliminary Proxmark3 support: `lf autel`

Because the air protocol is uniform — authenticate, write `0xFE`, write the image — none of the per-type knowledge needs to live in firmware. The client builds the page list for a type and the firmware just replays it over the cipher. The command set:

| Command | What it does |
|---|---|
| `lf autel list` | the emulated-type catalogue, each type's `0xFE` code and UID rule |
| `lf autel dump` | reads every page known to be used, with per-page agreement marks |
| `lf autel read -p <page> [-n <count>]` | arbitrary pages, `0x00`–`0xFF` |
| `lf autel write -p <page> -d <hex>` | one raw page, with read-back verify |
| `lf autel configure -t <type> [-u <uid>]` | writes `0xFE` then the type's image, in one session |
| `lf autel reset` | restores the factory type `9B290A9B` (ID4D) |
{: .wrap-cells }

All of them take `-k` for a blank whose device key is not the shared `9F63A5E8B14B`. Each of the 18 catalogue types was diffed against the trace it came from — page order and every constant matching byte for byte — and the firmware's cipher path was replayed against all 29 captures on the host, reproducing every session's `aR` and decrypting every frame with a passing check. It is **not yet exercised on real hardware**, though: the captures fix the protocol, the crypto and the images, but not the analogue timing margins.

## Still unknown

- The 40-bit opener `0x1001002E3E` and the slower modulation in the identify probe sweep — which transponder family is the Autel looking for there?
- Whether the AT100 accepts an arbitrary reader nonce or only the Autel's fixed `0xED355308`. The traces can't say; the Proxmark code tries a random nonce.
- The many untouched page ranges — real storage, or gaps? A `READ` sweep on hardware would settle it.
- The config word's redundant fields, and the type codes (`0x00`, `0x10`+) and menu entries (7935, ID8E, the MQB Renegade/4.5 variants, Reset) not present in these captures.
- Whether `9F63A5E8B14B` is on every AT100 ever made, or just this batch of five blanks.
