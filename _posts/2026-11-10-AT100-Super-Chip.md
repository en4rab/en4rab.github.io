## What the AT100 is

The AT100 is a **programmable HITAG2 transponder** — an emulator blank, sold for use with Autel key-programming tools, that can be configured to present whatever transponder identity a car expects. It is the Autel equivalent of the Xhorse super chips I looked at in the [XT27A]({% post_url 2026-10-29-XT27A-Super-Chip %}) and [XT136]({% post_url 2026-10-31-XT136-Super-Chip %}) posts, but the family resemblance stops at "programmable blank". Where the Xhorse chips invent a custom channel with their own `XHORSE`/`XMICRO` wake words and a bespoke LFSR cipher, the AT100 does something much plainer:

**it is stock HITAG2 all the way down.** HITAG2 BPLM from reader to tag, HITAG2 Manchester from tag to reader, and the ordinary Philips/NXP 48-bit stream cipher for authentication — the exact cipher the Proxmark3 already implements in `common/hitag2/hitag2_crypto.c`. There is no Xhorse channel-A LFSR and no `XMICRO` channel here. If you have ever sniffed a real HITAG2 car key, the air on these traces will look completely familiar.

What makes it an *emulator* rather than a plain HITAG2 tag is a **two-layer memory model** that the Autel drives once it has authenticated:

1. A **device / management key** `9F63A5E8B14B`, which turns out to be **shared across every AT100 blank** in these captures. The Autel authenticates to the chip's management interface with this key.
2. A separately-addressed **emulation image** — HITAG2-style pages reached through command addresses `0x200`+ — that the Autel reads and rewrites to change the identity the blank presents. The `set-id46` trace writes a factory **MIKRON / ID46** image into exactly these pages.

The device key is *not* the emulated key. Authenticating uses `9F63A5E8B14B`; the image that `set-id46` writes has its own HITAG2 key, `MIKRON` (`4F4E4D494B52`). The two live in different regions of the chip.

> This is a first look, decoded from six Autel captures and cryptographically verified, but not yet driven from a Proxmark3. Everything below was measured from the traces in the viewer; where something is inferred rather than observed it is called out.
{: .prompt-warning }

## The physical layer

Same sampling as the Xhorse traces: one `.pm3` sample is one T<sub>0</sub> = 8 µs (125 kHz, ADC after envelope detection).

- **Reader → tag: HITAG2 BPLM.** The field drops briefly before every bit; an `18–22` T<sub>0</sub> gap is a `0`, `26–32` T<sub>0</sub> is a `1`. *N* bits need *N+1* field-return edges.
- **Tag → reader: HITAG2 Manchester** (~`32` T<sub>0</sub> per symbol), opening with the HITAG2 `11111` start-of-frame. A 32-bit page reply runs about `1185` T<sub>0</sub> (≈9.5 ms).
- **Strong load modulation.** On some reads the tag's reply dips far enough to look like a reader field pulse, so a naïve decoder mislabels it as reader housekeeping. The decoder here uses a lower reader threshold (`-110`) so those replies survive.

The Autel resets the tag between almost every frame — field off for anywhere from 13 to 150 ms — so each line in the trace is effectively a fresh power-up.

## A session, start to finish

A read session has three phases, all visible in the Fig. 1 table:

**1. Probe sweep.** Every read opens with the same constant 40-bit reader frame `0x1001002E3E` (an Autel-specific wake/select that is not yet characterised), then a run of standard HITAG2 queries — `0011` (identify), `11000` (`START_AUTH`, sent three times), and a few more select/halt-class commands. The tag answers with short anticollision frames (`1110`, then runs of `FFFF…`). This is wake-up and anticollision, not payload.

**2. Page-0 read (cleartext).** Then, repeated a couple of times:

```text
R>T  1010                   4-bit handshake query
T>R  1010                   tag echoes
R>T  1111100000  = 0x3E0    10-bit HITAG2 read page 0
T>R  <32-bit UID>           e.g. 0x8358BE8C -- cleartext; page 0 is public
```
{: .nolineno }

This is just an ordinary HITAG2 read of page 0, the serial, which needs no crypto. Every blank in the captures reports a UID beginning with the byte `0x83`.

**3. Crypto session.** Finally the real authentication:

```text
R>T  {nR}{aR}  = 64 bits    nR = 0xED355308 (cleartext IV), aR = keystream(32) ^ 0xFFFFFFFF
T>R  <32-bit>               encrypted token (see below)
```
{: .nolineno }

The reader IV **`nR = 0xED355308` is identical in every session and on every tag.** The Autel always replays the same IV, so `aR` depends only on the tag's key and UID. That is the whole ballgame for recovering the key, and it is the single biggest difference from a well-behaved HITAG2 deployment, where the reader nonce should be random.

## The shared device key

Because the IV is fixed, each capture gives a clean `(UID, aR)` pair under a known nonce — exactly the input the standard HITAG2 state-recovery attack wants. Using the Proxmark3's own bundled tooling (`tools/hitag2crack/crack5`, the "HiTag2 Hell" bit-slice recovery) on one pair gives a 48-bit key, and then the repo's reference cipher checks it against the others. The result is the same key for **every** AT100 blank in the captures:

```text
key = 9F63A5E8B14B
```
{: .nolineno }

One key reproduces the observed `aR` for all five UIDs under IV `0xED355308`:

| UID (page 0) | aR observed | verifies |
|---|---|---|
| `8358BE8C` | `76D8A24C` | ✓ |
| `836BC7C7` | `53AFB236` | ✓ |
| `83240599` | `D421F8D0` | ✓ |
| `831CBB49` | `3E1E1B81` | ✓ |
| `836B61C0` | `C5CF2336` | ✓ |
{: .wrap-cells }

As a cross-check that the byte and bit conventions are right, the same cipher path reproduces the factory `MIKRON` (`4F4E4D494B52`) authentication on the XT136's post-reset HITAG2 image (UID `64B55D12`) from the previous post. This is the same cipher the decoder in Fig. 1 runs in your browser to peel the keystream off every encrypted frame — so you can watch each `aR` verify and each data page decrypt as you click through the table.

Whether this one key is baked into every AT100 ever made or is just shared across this production batch, I can't say from six captures. Either way, it is a management key, not the emulated key, so knowing it lets you talk to the blank's programming interface — not impersonate whatever car key it has been set to emulate.

## After auth: the 20-bit command format

Once authenticated, reader commands stop looking like HITAG2 and take a format of the AT100's own: a **10-bit word sent twice, true then bitwise-complemented** — `{W}{~W}`, a 20-bit frame with a built-in error check. The top two bits of the word are the opcode:

| Opcode (bits 9:8) | Meaning |
|---|---|
| `10` | **WRITE** page `addr` (low 8 bits), followed by a 32-bit encrypted data frame |
| `01` | **READ** page `addr` |
{: .wrap-cells }

Every command word and every data word is encrypted with the continuing HITAG2 keystream. The first thing the tag sends after a successful auth, before any command, is a 32-bit frame that decrypts to the constant **`0x9B290A9B` on every tag** — a factory config/password page the chip auto-returns in crypto mode.

In the **read / identify** sessions the Autel then issues a single read of a device-key page:

```text
R>T  READ word 0x1FC            20-bit {0x1FC}{~0x1FC}
T>R  <32-bit> = 0xA5E8B14B      constant across tags
```
{: .nolineno }

`0xA5E8B14B` is the **low 32 bits of the device key `9F63A5E8B14B`**. The Autel reads this page to confirm the blank is a genuine shared-key AT100 before it programs it. Note that the device key lives in its own page: reading it returns the key, not the emulated `MIKR`/`ON` bytes, which is the clearest evidence that the device key and the emulation image are separate regions.

## The write: `set-id46`

Decrypted, the write session is a clean config-plus-image write. Each write is acknowledged by a 20-bit tag echo of the command word before the 32-bit data frame goes out:

| Reader command (plaintext) | 32-bit data (plaintext) | Meaning |
|---|---|---|
| `WRITE 0xFE` | `8F08029B` | emulation config word |
| `WRITE 0x00` | `D52DA717` | new emulated serial |
| `WRITE 0x01` | `4D494B52` = `"MIKR"` | HITAG2 key, low |
| `WRITE 0x02` | `00004F4E` = `"\0\0ON"` | HITAG2 key, high |
| `WRITE 0x03` | `06AA4854` | HITAG2 config page |
{: .wrap-cells }

Pages 1–3 (`4D494B52 00004F4E 06AA4854`) are *exactly* the factory MIKRON / ID46 HITAG2 image — the same bytes the VVDI mini wrote on an XT136 reset in the [previous post]({% post_url 2026-10-31-XT136-Super-Chip %}). So `set-id46` makes the AT100 emulate a factory **ID46 (MIKRON-keyed)** transponder with a fresh serial in page 0. The password spells `MIKR` + `ON`, the same "`ONMIKR`" default the Xhorse chips ship with.

## What we know so far

- Air interface is **stock HITAG2** — BPLM reader, Manchester tag, the 48-bit NXP crypto. No custom channel, no custom cipher.
- The reader IV is **fixed** at `0xED355308`, so a single capture per blank is enough to recover the key.
- A **shared device key `9F63A5E8B14B`** authenticates the management interface on every blank in the captures.
- Memory is **two-layer**: a device-key region (read via word `0x1FC`, returns the key's low word `A5E8B14B`) and a rewritable **emulation image** at pages `0x200`+.
- The post-auth config/password token is the constant `0x9B290A9B`.
- Post-auth commands are 20-bit `{word}{~word}` frames: `0x2xx` = WRITE page, `0x1xx` = READ page.
- `set-id46` writes the factory MIKRON / ID46 image plus a new serial.

## Still unknown

- The 40-bit opener `0x1001002E3E`, and the meaning of the config words `0x9B290A9B` and `8F08029B` (the `0xFE` page).
- The full READ address map — only the device-key read (`0x1FC`) and the four written image pages appear; everything else is unmapped.
- Whether writing pages 1–2 (`MIKRON`) changes the AT100's *own* authentication key or only the emulated identity. The `set` trace ends before any re-auth, so this is inferred; the device-key read at `0x1FC` still returns `9F63…` rather than `MIKRON`, which argues for separate regions.
- How the shared device key is provisioned — whether every AT100 blank carries `9F63A5E8B14B` or only this batch.
